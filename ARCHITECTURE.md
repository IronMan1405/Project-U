# Project U — Architecture

## 1. Purpose

U is a lightweight, personal desktop assistant designed to help with everyday computing, studying, productivity, and engineering projects.

**Project deadline:** October 21, 2026  
**Development approach:** AI-assisted development using GitHub Copilot  
**Design principle:** Useful, lightweight, local-first, and maintainable.

U is a personal utility, not an autonomous AI agent or a general-purpose operating system.

## 2. Technology Stack

- **Language:** Python
- **LLM runtime:** Ollama
- **LLM:** Existing locally installed model
- **Database:** SQLite
- **Interface:** Local Flask web UI at `http://127.0.0.1:5000` plus a terminal client (`main.py`)
- **Version control:** Git and GitHub

Prefer existing capabilities and minimal dependencies. Do not introduce additional frameworks without a clear need.

## 3. Core Architecture

### Assistant Core
Coordinates user input, context, model requests, and tool execution. `assistant_runtime.py` keeps one in-memory history per conversation (user messages, tool requests, tool results, and replies); it is session-scoped, never persisted, and lost when the server or terminal client restarts. Each model request is ordered profile, fixed rules (`SYSTEM_RULES`), earlier turns, then the per-request date/time and document context, then the current turn, so Ollama can reuse its prompt cache for the unchanged prefix; the per-request context is never stored. Before each turn, history over `MAX_HISTORY_CHARS` (48,000 characters) is trimmed toward `HISTORY_TRIM_TARGET_CHARS` (28,800) by dropping the oldest complete turns (cut only at user messages, so a tool request and its result stay together; the newest turn is always kept), and stored tool requests omit the model's hidden "thinking".

The system message after the profile is `system_prompt(model)`: `identity_prompt(model)` (who K.R.I.S. is, its personality, when it may use its signature line, and honesty about the configured local model) followed by the unchanged `SYSTEM_RULES`, which take precedence. It is one stable message in every request (typed and voice turns share `/api/chat` and the runtime; tool rounds and follow-ups reuse it), is never stored in the history, and keeps Ollama's prompt cache valid. The signature line is only ever written by the model; no code inserts it. `tests/test_identity.py` checks the assembly deterministically; `LIVE_MODEL=1` adds checks against the real model.

Confirmation outcomes are deterministic. A declined action, and every tool call queued after it in the same request, gets a "not run" result and the turn ends with fixed text from `_cancel`, without asking the model; if earlier actions in that request already ran, the text says so. A new message while a confirmation is pending performs that cancellation and starts the new turn under the same per-conversation lock as `resolve_confirmation`, so the old confirmation ID is invalid afterwards and the two can never interleave; the cancellation text is returned as `TurnResult.notice`. Confirm and Cancel remain the other ways to resolve a pending action.

### LLM Client
Communicates with the local Ollama API. Keeps model configuration separate from application logic.

### Context
Loads the user-editable `profile.json` before each model request and provides its validated preferences as separate system context alongside the in-memory conversation. The web client can also attach one explicitly uploaded `.txt` or `.pdf` to a conversation. `documents.py` validates and extracts uploads locally in memory; question-relevant page/paragraph excerpts are passed as separate untrusted document context through the shared Ollama request path, capped at 12,000 characters. Replacing the selected document resets that conversation's history. Profile values are user data, not instructions or authorization. Missing or invalid profiles use generic defaults.

### Memory
`storage.py` owns the SQLite schema and parameterized CRUD operations for tasks and notes. Tasks have an optional `due_at` (`YYYY-MM-DD` or a UTC `YYYY-MM-DD HH:MM:SSZ` timestamp), validated by `storage.validate_due_at` and shared by the API, tool schemas, and UI; older databases gain the column on startup. `update_task` changes only the fields it is given, so completing a task never alters its due date. The assistant tools accept due times as local wall-clock values (`YYYY-MM-DD HH:MM`, or with an explicit offset); `storage.normalize_due_at` converts them to UTC in Python using the system time zone and rejects times that a daylight-saving change skips or repeats, so the model never does timezone arithmetic. The web API itself accepts only the canonical formats. The default database is `data/project_u.sqlite3`, created automatically and kept local. Flask exposes explicit task and note APIs used by the web interface; chat changes these records only through the registered tools in `tool_registry.py`.

### System telemetry
`system_telemetry.py` reads macOS telemetry with the standard library only, never through a shell: CPU utilization from `host_statistics(HOST_CPU_LOAD_INFO)` via `ctypes`, memory from `/usr/sbin/sysctl` (`hw.memsize`, `kern.memorystatus_vm_pressure_level`) and `/usr/bin/vm_stat`, GPU utilization from the undocumented "Device Utilization %" in `/usr/sbin/ioreg -r -d 1 -c IOAccelerator`, and the thermal pressure level from `NSProcessInfo.thermalState` through the Objective-C runtime (`ctypes`). Programs run by fixed path with argument lists and a 1.5-second timeout; missing programs, timeouts, permission errors, non-zero exits and malformed output become a fixed, display-safe "unavailable" message, never zero and never raw output. `CpuSampler` takes CPU samples on a daemon thread every 2 seconds (started on first use, stoppable for tests), so requests never wait; until two samples exist the CPU reads "sampling", and a sample older than three intervals is discarded rather than averaged over a long gap. `TelemetryService` caches memory, GPU and thermal readings for 2 seconds with one lock per metric, so concurrent requests share one read and one failing metric never affects the others. `shared_service()` gives the web app and `get_system_info` the same sampler. `GET /api/system/telemetry` returns `{"platform_supported", "refresh_seconds", "metrics": {"cpu", "memory", "gpu", "thermal"}}`, each metric with a `status` of `ok`, `sampling` or `unavailable` (documented in the module docstring), sent with `Cache-Control: no-store` and covered by the existing host and Origin checks. In the browser, `static/telemetry_view.js` (DOM-free, tested with `node --test`) formats each metric, and `static/app.js` polls every 3 seconds with one request at a time, only while the page is visible, rendering with `textContent` and `title`.

### Google Workspace provider
`google_workspace.py` is the provider for the organisation's Google Workspace (Gmail and Google Calendar), separate from any Apple provider (none exists yet), and uses the standard library only. It is opt-in through the `[google]` section of `config.ini` (`load_google_settings`), which names a Desktop-app OAuth client file kept outside the repository and an optional `workspace_domain`. `POST /api/google/connect` (same-origin) creates a single-use `state` and a PKCE verifier held in memory for 10 minutes and returns Google's consent URL; Google redirects to `GET /oauth/google/callback` on `127.0.0.1`, which checks the state, exchanges the code, checks the ID token's issuer, audience, expiry, verified email and `hd` domain (revoking the token on a mismatch), and stores the refresh token, granted scopes and email in the login Keychain through `/usr/bin/security -i` over stdin, so the token never appears in a process's arguments. Access tokens are kept in memory and refreshed on demand; a 401 triggers one refresh and retry, and `invalid_grant` deletes the stored token and reports "connect again". Google's errors are mapped to fixed messages (not enabled, scope not granted, Workspace policy, rate limit, outage, network) and never include Google's text, tokens or private data. Scopes are derived from `CAPABILITIES` (`identity`, `inbox.read` via `gmail.metadata`, `calendar.read` via `calendar.events.readonly`); `FUTURE_CAPABILITIES` lists the write scopes for later stages, which are not requested. Adding one means enabling its capability: `status()` then reports the missing scope and the user reconnects (incremental consent with `include_granted_scopes`). `GET /api/google/status`, `/api/google/inbox` and `/api/google/calendar` return display data only, cached for 60 seconds, with `Cache-Control: no-store`; `POST /api/google/disconnect` revokes and forgets. In the browser, `static/google_view.js` (DOM-free, tested with `node --test`) formats status, inbox and calendar values, and `static/app.js` renders them with `textContent`, polling only while connected and visible. Stage 2 adds Gmail draft creation (`mail.draft`, scope `gmail.compose`) and raises `CONSENT_VERSION` to 2: a stored connection without that version is reported as `reconnect_required` and every read or draft raises a `reconsent` error until the user reconnects. The model's only Google tool is `create_gmail_draft` (registered only when `[google]` is set up), with `always_confirm=True`. Its `prepare` step calls `prepare_draft`, which validates the model's fields (plain addresses only, at most 20, a one-line subject, a plain-text body of at most 6,000 characters, no line breaks in headers) and, for a reply, reads the original message's headers (`gmail.metadata`) to fill in the thread ID, In-Reply-To, References, the default recipient and "Re:" subject. The resolved draft becomes the prepared call's arguments and its `preview`, which `AssistantRuntime` returns in `pending_confirmation` and the web UI shows in full in the confirmation panel. After the user confirms, `create_draft` re-validates and writes exactly those arguments with one `drafts.create` call (an RFC 5322 message built with `email.message.EmailMessage`), retrying once on 401. There is no send, modify or generic Gmail tool; `CONSEQUENTIAL_OPERATIONS` lists `create_gmail_draft` and the future write tools, `tool_registry.check_confirmation_boundaries` refuses to register any of them without `always_confirm`, and `perform()` refuses every other write operation. Inbox results now include each message's Gmail ID, used by the Inbox tab's Draft reply action. Stage 3 adds `mail.read` (`gmail.readonly`) and `mail.modify` (`gmail.modify`) and raises `CONSENT_VERSION` to 3. `search_gmail` passes the model's query to Gmail's server-side `messages.list?q=` with at most 10 results and fetches only each match's headers (`format=metadata`), never a mailbox listing or bodies; `read_gmail_message` fetches one message (`format=full`) or, with `include_thread`, the message's thread ID (`format=minimal`) and then that one thread, extracting text/plain (or text/html converted to text without scripts), listing attachment names, and shortening bodies until the result fits the tool-result limit (`_fit`, at most the latest six thread messages), with a note that email content is untrusted. Both are read-only and run without confirmation. The mailbox actions are eight separate always-confirmed tools, one per entry in `GMAIL_ACTIONS` (`mark_email_read`, `mark_email_unread`, `star_email`, `unstar_email`, `archive_email`, `trash_email`, `add_label`, `remove_label`), each on exactly one message: `prepare_action` validates the ID, reads that message's headers and thread, and for labels resolves an existing *user* label by name (system labels are refused and labels are never created); the result is the prepared call's arguments and a `gmail_action` preview naming the action, message and thread, shown in the confirmation panel. After approval `apply_action` makes one `messages.modify` call with label changes fixed by `GMAIL_ACTIONS` (or one `messages.trash` call) and clears the inbox cache. There is no `messages.delete`, `batchDelete`, `batchModify`, send, or generic Gmail call anywhere; all eight action tools are in `CONSEQUENTIAL_OPERATIONS`, so `check_confirmation_boundaries` refuses to register any of them without `always_confirm`. A 404 now maps to a `not_found` error, and a 403 whose message mentions Gmail's metadata scope maps to `metadata_scope` (Google is reported to let `gmail.metadata` restrict a token that also has `gmail.readonly`; real-account use has not shown it). Stage 4 adds `mail.send` (`gmail.send`) and `calendar.write`, and Calendar reading now uses `calendar.events` instead of `calendar.events.readonly`; `CONSENT_VERSION` is 4. Sending is four always-confirmed tools (`send_email`, `reply_to_email`, `forward_email`, `send_gmail_draft`): `prepare_send` builds the final message (recipients incl. Bcc, at most 20 in all; reply/forward threading from the original's headers; a forward quotes the original text and lists, but does not attach, its attachments; a draft is read in full) and stores a SHA-256 `fingerprint` of everything shown; the preview is a `sections` preview of exactly those fields. `send_message` refuses if the fingerprint no longer matches, re-reads a draft and refuses if it changed, then makes one `messages.send` (or `drafts.send`) call; failures say the email was not sent. Draft IDs for `send_gmail_draft` must come from `list_gmail_drafts` or `create_gmail_draft` results in the same conversation (`ToolRegistry._seen_draft_ids`). Calendar has two read tools without confirmation, `search_calendar_events` (any `timeMin`/`timeMax` range and optional `q`, default start now, up to 25 results, with an ambiguity note when several match) and `read_calendar_event`, and three always-confirmed changes: `create_calendar_event` (future only; wall-clock times in an IANA time zone, default this Mac's), `update_calendar_event` and `delete_calendar_event` (future, non-series events only; event IDs must come from Calendar results in the same conversation, `_seen_event_ids`). Updates and cancellations are prepared from a fresh `events.get` (the preview shows Before and After from that copy) and store its `etag`; immediately before writing, `_revalidate` fetches the event again and aborts with a `stale` error if it is gone or its etag changed, and the PATCH/DELETE also carries `If-Match`, so a concurrent change is never overwritten (Google's 412 maps to `stale`). `sendUpdates` is `all` when the event has attendees. The Calendar panel (`GET /api/google/calendar?days=14|30`) is a display range only; the tools have no date limit. v1.3 does not include Google Keep: it was deferred because Google refuses the `keep` scope for personal accounts (`invalid_scope`; the API is for Workspace organisations), so `CONSENT_VERSION` stays 4 and there are no Keep scopes or tools. For workflows, `MAX_TOOL_EXECUTIONS_PER_TURN` is 6 and `MAX_MODEL_ROUNDS_PER_TURN` 10, and `SYSTEM_RULES` tells the model that every consequential action is approved separately, chat words are not approval, partial results must be reported exactly, references ambiguous across earlier results must be asked about, and failed actions keep their prepared content; each turn records the writes and confirmed actions it ran (`_TurnState.changes`), and the fixed replies used when a turn cannot end with a model reply (model failure, round limit, a cancellation after earlier actions) list exactly what completed and what failed (`changes_report`); the runtime already confirms queued actions one at a time and cancels the rest when one is declined. In the UI, the lower right panel's tabs are Activity and Alerts (the Alerts list, empty state and count moved there unchanged); the Utilities tab and the separate Alerts box are gone.

### Tools
Provides narrowly scoped functions for approved operations, such as managing tasks, reading selected files, and opening applications. `computer_utilities.py` holds the approved computer utilities: `config.py` loads allowlisted folders and macOS apps from `config.ini`, and `tool_registry.py` offers `find_files` (bounded, read-only file-name search; a multi-word search with no results is retried once with recognized file-type words such as "spreadsheets" turned into an extension filter, within the same entry limit), `open_file` (confirmed, path-contained, document types only), and `open_application` (confirmed, allowlist only) only when they are configured. Launches use the fixed `/usr/bin/open` executable with argument lists, never a shell.

### UI
Provides a single, consistent interface for interacting with U, presented in the web UI as the K.R.I.S. command center. `templates/index.html` lays out a CSS grid under a header with the centred wordmark: a left column with two boxes (an always-visible System panel with live CPU, memory, GPU and thermal rows and, beneath a divider, a live HH:MM clock and date (`updateClock()`, checked once a second); and a switchable Inbox / Calendar panel with honest "not connected" states), a centre column that holds only the energy core and its status, a right column with the workspace panel (Chat / Tasks / Notes / Files), a read-only console, and a switchable Activity / Alerts panel, and the command bar (composer, microphone, voice controls, errors) across the bottom. The two side columns share one width (`--side-column`), so the centre column and the core sit on the page's horizontal centre. Below 1180 px the core and the left boxes share one column; at 820 px and below everything stacks into a single scrolling column with a sticky command bar. Every element ID that `static/app.js` already used is kept. The Chat, Tasks and Notes view panels moved unchanged into the workspace panel, and the document controls moved into a new `#files-view` panel, so `switchView()` works as before: it hides every `.view-panel` except `#<name>-view` and loads tasks or notes on demand. Because the core is outside those panels, navigation never replaces it. `static/style.css` defines design tokens on `:root` (colours, spacing, borders, typography), and the core is an inline SVG animated only with CSS (no 3D engine and no new dependencies), styled by its `data-state`. A final "HUD visual layer" section in the stylesheet restyles the existing panels (hairline borders, four corner brackets from one pseudo-element, `data-section` identifiers, tab and readout typography) and adds a fixed, inert `.hud-frame` around the viewport. The core sits inside `.core-instrument`, a second decorative SVG (tick ring, segmented arcs, an orbit marker, an amber attention arc) that takes its size from the existing breakpoints. `renderCore()` copies the core's state onto it, and the LINK, MODE and LAST EVENT readouts are filled from the health check, the Hands-free toggle and `logActivity()`; none of this feeds back into behaviour.

The command-center panels only display facts the page already has and never change behaviour. `renderVoiceView()` also calls `renderCore()`, which takes the state from `VoiceLoop.viewState()` (not limited to voice, so typed requests still show Thinking). It shows Waiting for confirmation while the Confirm/Cancel panel is open, and Offline when `/api/health` fails and nothing else is happening. `renderAlerts()` rebuilds the alert list from the health result, the visible error message, the confirmation panel (watched with a `MutationObserver`, since several code paths hide it) and the loop's `notice`. `logActivity()` appends timestamped lines (tool activity, core state changes, errors, model status changes) to an in-page list capped at 60 entries. The model status appears in the header and the core's LINK readout, both from `/api/health`; there is no hardware telemetry API. The live "thinking" status from the runtime still says "U is thinking...", so the browser shows it as "K.R.I.S. is thinking..." instead. `showChatView()` returns to the transcript when a message is sent or a confirmation appears, so the persistent command bar never sends into a hidden view. The two side panels marked `[data-tabs]` use `setupPanelTabs()`, a standard ARIA tab list (`aria-selected`, roving `tabindex`, arrow keys, Home and End) that only shows and hides panes; the alert count beside the Alerts heading comes from `renderAlerts()`.

### Voice
`voice.py` adds optional, local push-to-talk. `POST /api/voice/transcribe` converts a browser recording with FFmpeg, measures its loudness with `speech_level` (standard library only; recordings with less than `MIN_SPEECH_SECONDS` at or above `SPEECH_LEVEL_DBFS` are rejected as "No speech was detected" without running whisper.cpp, because whisper transcribes silence as "you"), and otherwise transcribes it with whisper.cpp (`ggml-base.en`). It returns text plus a deterministic `reply_kind` (`affirm`, `decline`, or null) from `classify_reply`, which matches only a whole short reply such as "yes" or "no". The server never acts on `reply_kind`; the browser uses it while a confirmation is pending: `affirm` is not sent (approval stays button-only) and `decline` calls the Cancel path. Otherwise the transcript is placed in the message box for review, or, in the opt-in Hands-free mode, sent automatically through the normal `/api/chat` path, so tool rules and confirmations are unchanged. `POST /api/voice/speak` turns replies, confirmation prompts and cancellation messages into WAV audio with macOS `say` when spoken replies or Hands-free are on. In Hands-free mode the browser also detects the end of speech: `static/voice_activity.js` is a small DOM-free state machine (tested with `node --test tests/js/`) fed one level per 50 ms from a Web Audio `AnalyserNode` on the same `MediaStream` the `MediaRecorder` records. It measures a per-recording noise floor, recognises speech onset and a trailing silence of `end_silence_ms` (after `min_recording_ms`), and discards recordings with no speech within `NO_SPEECH_TIMEOUT_MS` without uploading; `max_seconds` remains the hard cap. The timings come from `[voice]` via `GET /api/voice/status`. In `static/app.js`, every way a recording ends goes through `stopRecording(reason)` (first reason wins) and `teardownRecording()`, which stops all tracks, the analyser, and timers; a session counter ignores late callbacks, and hidden pages, page exit, and an ended microphone track discard the recording. The transcribe and speak endpoints run fixed executables with argument lists and timeouts, keep audio and text only in a temporary directory for the request, and are configured by the optional `[voice]` section in `config.ini`.

The Hands-free listening loop is owned by `static/voice_loop.js`, a DOM-free reducer (also tested with `node --test tests/js/`) with the states `off`, `listening`, `transcribing`, `thinking`, `speaking`, and `awaiting_confirmation`. `static/app.js` only reports events to it (`dispatchLoop`) — the user's tap, recordings uploaded or discarded, transcript outcomes, chat and confirmation results tagged with a turn number, playback ending or failing, Hands-free off, page hidden, typed messages — and carries out the actions it returns (`start_listening`, `stop_listening`, `stop_playback`, `notify`). Only a tap starts the loop; it resumes listening only from `speaking` (when that turn's playback ends) or from `thinking` (an unspoken reply), never while awaiting a confirmation or while a request is in flight; events from an earlier turn or the wrong state are ignored, and every failure or two consecutive silences return it to `off` with a message. `speakReply()` returns a promise (true when playback ends, false on failure, null when stopped or replaced), Confirm and Cancel are disabled while a recording is being transcribed, and a hands-free transcript that arrives while another request is running is kept in the message box instead of being submitted.

The voice indicator above the message box (Listening, Transcribing, Thinking, Speaking, Waiting for confirmation, Hands-free paused, Error) is derived, never stored: `VoiceLoop.viewState(loop, facts)` returns the state from the loop while Hands-free runs, and otherwise from read-only page facts (recording, transcribing, a request in flight, a spoken reply in progress, an error showing), so Review mode is covered without a second state machine. The loop keeps a `notice` (kind `paused` for silence or a busy page, `error` for failures) for the paused/error display, cleared by the next tap or by switching Hands-free off. `renderVoiceView()` in `static/app.js` updates the indicator — a polite, atomic `role="status"` region whose text changes only when the state changes — and shows the Stop Speaking button only while a spoken reply is being prepared or played. Stop Speaking dispatches `stop_speaking`: the loop always returns `stop_playback`, and only from `speaking` (a hands-free reply) also moves to `listening` with a single `start_listening`; the cancelled playback promise then resolves after the loop has left `speaking`, so its stale `playback_finished` is ignored. In Review mode, during a spoken confirmation prompt, or when nothing is playing, it only stops (or ignores) playback and never starts listening.

Barge-in reuses the existing paths rather than adding a state machine. While a spoken reply plays the mic stays enabled (labelled "Interrupt and talk" in Hands-free); `micPressStart()` dispatches `start` (the loop moves from `speaking` or `awaiting_confirmation` to `listening` with no actions) and then calls `startRecording()`, which calls `stopReplyAudio()` before opening the microphone, so the tap itself is the only recording start and the interrupted playback's promise later resolves as a stale `playback_finished` that the loop ignores. A failed start dispatches `listen_failed` (loop `off` with an error notice, no retry). The loop carries a `confirmationPending` flag, set in `awaiting_confirmation` and kept only through `listening` and `transcribing`, so a recording discarded as silent after interrupting a confirmation prompt returns to `awaiting_confirmation` instead of asking to listen again; transcripts still go through the existing `reply_kind` rules (affirm guarded, decline → Cancel, anything else → normal chat). In Review mode the loop is off, so pressing the mic only stops the audio and records while held. Because a guard or cancellation message can follow an interrupted synthesis immediately, `speakReply()` retries `POST /api/voice/speak` on 429 (the server's one-synthesis-at-a-time limit) up to 12 times at 250 ms intervals while the request is still current. Gemma generation is not interruptible: the mic is disabled while a chat request is in flight.

The wake word ("Kris") is a second way to start that loop. `static/wake_word.js` (DOM-free, tested with `node --test`) holds its state machine (`off`, `starting`, `standby`, `checking`, `activating`, `active`, `paused`, `denied`, `error`; only the user's "enable" leaves `off`, `denied` or `error`), `standbyAllowed` (page visible and no recording, transcription, spoken reply or hands-free conversation), a burst detector that reports only short isolated sounds (about 0.15–1.4 s, padded with pre/post roll), a sample ring buffer, and 16 kHz WAV encoding. In standby `static/app.js` opens its own `getUserMedia` stream into an AudioWorklet (`static/wake_capture.js`) that only forwards samples; for each short sound it posts a WAV clip to `POST /api/voice/wake`, which runs `voice.detect_wake_word` (FFmpeg with the `wav` demuxer and a 2.5 s limit, whisper.cpp, then `is_wake_phrase`: the transcript must be just the name, `kris`/`chris`/similar spellings, optionally after "hey"/"okay") under the same one-at-a-time transcription lock and returns only `{"wake": bool}`; the transcript is never returned or logged. On a wake, standby stops its stream before the acknowledgment is spoken, then the loop is started with `{type: "start", maxSilences: 1}` and `startRecording(true)`, as a tap would; recordings in that conversation use `wake_follow_up_ms` as the no-speech timeout, so one silent window ends it. `syncWake()`, called on every voice render, suspends or resumes standby as the page facts change and returns to standby when the loop is off again. Microphone denial, a lost track, or three failed checks switch the wake word off with an alert; it is off on every page load.

Spoken replies come from Kokoro-82M through `kokoro_speech.py` (kokoro-onnx on the CPU with 4 inference threads; one engine per model/voice configuration, loaded once per process, preloaded on a background thread by `voice.preload_speech` when the server starts). The engine keeps one phonemizer `EspeakBackend` for its lifetime (the default `phonemizer.phonemize()` rebuilds espeak-ng on every call, which cost more than the inference), refuses espeak-ng data paths longer than its internal buffer before touching espeak-ng (which would otherwise exit the process), serializes inference with a lock, and appends a short silence after each segment by its final punctuation. `voice.synthesize` uses it when `kokoro_configured` (both model files found; defaults under `data/models/`) and falls back to `say` per request if Kokoro fails; errors are logged without the text. `voice.speech_text` rewrites each line for the voice only (email addresses, titles, initials, clock times, a.m./p.m., money and thousands separators, dates as ordinals, plain decimals), because Kokoro pauses at every full stop, colon or comma inside a word; `voice.speech_segments` splits a reply at sentence ends (not after abbreviations, initials, decimals or before a lowercase continuation), gives unpunctuated lines a full stop, splits long sentences at clause breaks and a long first sentence at its first clause break, joins tiny pieces, and caps a reply at `MAX_SPOKEN_REPLY_CHARS`. `POST /api/voice/plan` returns those segments without synthesizing; `POST /api/voice/speak` synthesizes one. In `static/app.js`, `speakReply` keeps its contract (one promise for the whole reply, `replyFinish` set throughout, so Stop speaking, barge-in, the hands-free loop and wake standby see one continuous reply): it plans, synthesizes the first segment, then synthesizes segment n+1 while segment n plays, one request at a time; `stopReplyAudio` aborts the in-flight request through an `AbortController` and nothing further is requested.

## 4. Safety and Privacy

- Prefer local processing and local storage.
- Never execute arbitrary shell commands generated by the LLM.
- Speech recognition and speech output run locally; recordings and transcripts are never stored or logged (only per-recording loudness numbers are logged, at INFO level).
- State-changing requests (POST, PATCH, DELETE) whose `Origin` is not U's own page, or that are marked `Sec-Fetch-Site: cross-site`, are refused with 403 before any work is done, so other websites cannot trigger uploads, transcription, speech, or tool actions; requests without an `Origin` (curl, the terminal, tests) are unaffected.
- Validate tool arguments before execution.
- Require explicit user confirmation for consequential actions.
- Restrict file access to user-approved locations.
- Never store API keys, passwords, or secrets in source control.
- Do not send personal files to external services without explicit user approval.
- Keep the local SQLite database out of version control.
- Task and note changes come from explicit UI/API requests or validated tool calls; model-requested writes run directly only for clear user requests and otherwise require confirmation.
- Only the Confirm button (or answering "y"/"yes" at the terminal's confirmation prompt) approves an action; cancelling, or sending a new message while one is pending, never runs it or anything queued after it.
- Uploaded documents are processed locally; request parsing may temporarily spool upload data, but no file is retained after the request. Extracted text is conversation-scoped memory only and is never added to profile or SQLite storage.
- Limit document uploads and extracted context; scanned PDFs are not OCR'd and large documents may be represented only by selected excerpts.
- The web server binds to `127.0.0.1` and accepts only the `127.0.0.1` and `localhost` Host names (Flask `TRUSTED_HOSTS`), so pages on other hostnames, including DNS-rebinding pages, cannot read data or approve actions.

## 5. Development Rules

- Implement one small feature at a time.
- Keep modules simple and responsibilities clearly separated.
- Test each feature before adding the next.
- Avoid unnecessary abstractions, agent frameworks, and dependencies.
- Do not add features outside the agreed MVP.
